# Progress documents

Every app keeps a small set of progress docs so any agent can pick up where the last left
off. The set:

| File | Role |
| --- | --- |
| `ROADMAP.md` | Committed one-page summary: stage, parity numbers, what's next |
| `docs/roadmap.md` | Milestones, **current focus**, estimates |
| `docs/target-app-parity.md` | The authoritative parity assessment: numbers, weights, evidence |
| `docs/gaps.md` | Every known shortfall, ranked — the work list to pick from |
| `docs/*-parity.md` | Per-dimension checklists (ui, file-format, hardware, localization, …) |
| `docs/parity-checklist.md` | **Generated** menu/feature coverage (never hand-edit) |
| `docs/scorecard.md` | **Generated** scorecard: perf budgets, corpus floors, dead settings |
| `log/devlog.md` | Terse dev log: what landed, what's still open |

## Rules

- When work lands, **update the rows it moves** — same commit: the parity doc, the gap entry,
  status lines and revision history, each with the date.
- Generated docs (`parity-checklist.md`, `scorecard.md`) are regenerated by
  `cargo xtask parity` / `cargo xtask scorecard` and committed; CI checks they are current.
- Floors only rise: when parity or a corpus pass-rate improves, raise the `FLOOR`/budget —
  never lower it.
- Pick work from the top of `docs/gaps.md` and `docs/scorecard.md`'s `missing`/`partial`
  rows; prefer measured numbers over estimates.
